# Campaign-state templates

Cross-campaign primitives for long-running COMSOL research workspaces.
Lifted from real workspaces where the same primitives keep being
reinvented.

| File | Purpose |
|---|---|
| [`findings_register_template.md`](findings_register_template.md) | Schema for `<campaign>_findings_register.md` — the running list of `F-DOMAIN-PHENOMENON-α` findings |
| [`campaign_state_template.json`](campaign_state_template.json) | JSON schema for `<campaign>_campaign_state.json` — orchestrator-visible state |
| [`finding_naming_convention.md`](finding_naming_convention.md) | The `F-DOMAIN-PHENOMENON-α/β/γ` convention with examples |
| [`STRUCTURE_template.md`](STRUCTURE_template.md) | Campaign-workspace directory layout |

## Usage

Copy the template you need into a new campaign workspace and rename:

```bash
cp <comsol-support>/templates/findings_register_template.md \
   /path/to/my-campaign/my_campaign_findings_register.md
```

These are deliberately format-only — they don't ship campaign-specific
content. The Source-N escalation lifecycle and the F-* ID convention
are generic across COMSOL research campaigns.

## Why these aren't generated by a CLI

Campaign bootstrap is rare (once per campaign, weeks of work each), so
a one-time copy + edit is friction-free. A `comsol-support
init-campaign` command would add code surface for negligible time
savings; revisit if the bootstrap step becomes routine.
